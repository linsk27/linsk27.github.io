竞见：把零散外宣材料变成可追溯的竞品情报

竞见是一套基于 Next.js、Supabase 与 OpenAI Responses API 的竞品外宣情报工作台，重点不在自由对话，而在查重、审核、证据编号、分析版本和外部 AI 回填闭环。

做竞品研究时，真正麻烦的通常不是“网上没有信息”，而是信息散在公众号、活动页、小红书、官网新闻和同事手里的截图里。链接会失效，同一场活动会被不同平台重复转载，表格里的机构名称也经常不统一。等到要写月报时，大家又要重新确认：这句话来自哪一条素材，是事实、推断，还是模型自己补出来的？

竞见就是围绕这条链路做的一套留学行业竞品外宣情报工作台。它把单条投递、批量导入、公开网页监测、人工审核、结构化分析和报告选材放进同一个系统里，并尽量让每个结论都能回到原始链接、正文、截图和稳定的证据编号。

先把“智能体”的定位说准确

竞见不是一个会自己拆任务、反复规划、长期记忆和自由调用工具的多智能体框架。当前代码里没有 Planner、ReAct 循环、向量知识库或多角色协作。AI 只出现在两条受控流程中：一条负责搜索最近的公开外宣动态，另一条负责把单条素材整理成固定结构的分析结果。

这里最重要的不是让模型“更自主”，而是限制模型只能在有来源、有状态、有人工确认的位置工作。系统本身负责数据一致性、权限边界、版本和失败处理，模型只负责它擅长的提取与归纳。

一条外宣素材怎样进入证据库

首页投递不是点一下就直接写数据库。用户先填写机构，并提供链接、正文或附件，然后调用预览接口。系统会尝试把机构名称映射到标准机构或别名，再推断平台、生成建议标签并检查重复。

查重没有依赖模型，而是用了几组可以复现的规则：

  • URL 会移除锚点和 utm_*、spm、from 等追踪参数，再统一主机名、路径和查询参数顺序；
  • 标题与正文标准化后计算 SHA-256，用来识别内容相同但链接不同的记录；
  • 在同一机构下继续比较标题，补上人工复制内容时容易出现的重复；
  • 发现重复后默认阻止入库，只有用户明确确认，才能把它保留成独立素材。

正式入库时，每条素材都会得到一个 EVD-... 证据编号。采集、审核、分析、人工复核和报告使用情况也不再挤在一个模糊的 status 字段里，而是拆成五组状态。这样“已入库但未分析”“模型失败但规则结果可用”“已分析但还没人工确认”就不会被混成一件事。

截图、PDF、文本和 DOCX 等附件保存在 Supabase 私有 Storage 中。上传接口限制 MIME 类型和 20MB 大小，用随机对象名落盘；数据库写入失败时会把刚上传的对象清掉。查看详情时生成短期签名链接，而不是把 Bucket 公开成静态目录。

公开监测为什么先进入审核箱

监测任务在免费部署下采用手动触发。用户选择机构、地区和关键词后，服务端调用 OpenAI Responses API 的 web_search，要求返回最近 30 天可核实的标题、URL、来源、平台、摘要和时间。

搜索结果不会直接变成正式素材。系统会先记录一次 monitoring_runs，按标准化 URL 去重，再把最多 30 条结果写入 raw_leads。之后用户在审核箱里逐条打开原始链接，修正机构、平台、标题和标签，并选择忽略、合并到已有素材、合并到宣传事件，或者确认入库。

这一步看起来比“自动抓取后直接分析”多了一道手续，但它解决了两个实际问题：公开搜索可能把转载当成新事件，也可能只拿到摘要而没有完整正文。把模型结果先当线索，而不是当事实，是这套系统最关键的边界之一。

如果没有配置 OpenAI、额度不足、地区不可用或响应格式解析失败，运行记录会保存明确错误码。页面会提示继续使用手工投递和批量导入，不会为了让看板好看而伪造一批“自动发现”。

AI 分析不是一次 JSON 写回就结束

素材分析同样是一条单次、受约束的调用。Prompt 要求模型把结果拆成事实、内容标签、营销策略、目标客群、转化路径、策略信号、行动建议和证据编号，并明确样本不足时留空。

服务端不会直接相信模型返回的 JSON。解析后还会做一层收口：内容标签和营销策略只能落在预设白名单里，数组字段统一转换，置信度限制在 0 到 1，当前素材的证据编号也会强制写入结果。随后系统分别保存 analysis_results、analysis_versions 和 analysis_evidence，记录模型名、Prompt 版本、结构化数据、错误和人工复核状态。

内部模型失败时，系统会运行一套简单的确定性规则。例如出现“白皮书、报告、活动、录取、限额、预约”等词时，生成低置信度的基础标签和待核建议。规则结果不会冒充模型成功：失败版本和规则版本会同时保留，素材状态也会标记为额度不足、模型不可用或分析失败。

这套实现没有 RAG，也没有把关系型数据库包装成“长期记忆”。它保存的是更朴素、也更容易审计的东西：原始材料、分析历史、证据关联和人工确认记录。

内部模型不可用，也不把流程卡死

竞见里最有意思的部分，是外部 AI 的导出与回填。

用户可以按素材、机构、时间、导入批次或报告项目选择范围，生成一个 ZIP 交接包。里面不仅有一段提示词，还包含素材的 XLSX、Markdown 和 JSON 版本、机构背景、已有分析、回填模板、证据索引，以及已经入库的附件。单次同步请求最多处理 1,000 条素材，并把附件控制在大约 80MB；更大的任务需要按机构或时间拆分。

这个包可以交给 ChatGPT、Claude、Gemini、DeepSeek 或其他模型。外部模型完成后，用户把 XLSX 或 JSON 结果重新导入。系统按 material_id 或 evidence_id 匹配原素材，并把结果保存成 external:<模型名> 的新版本。遇到冲突时默认两个版本并存，不覆盖原始素材，也不覆盖之前的内部分析。

这比在页面里塞一个聊天框更接近真实工作：模型可以替换，证据格式和回填契约保持稳定；在线 API 暂时不可用时，业务资料仍然能整理、审核和交接。

竞品档案和报告如何避免“看起来很懂”

竞品档案不是让模型凭空写一段机构画像，而是从已经入库的素材和宣传事件中聚合主题、平台、产品、客群和营销策略。趋势也使用可解释的简单口径：比较近 30 天与此前 60 天的月均数量；有效样本少于 4 条时，直接显示“数据不足”。

报告中心保存时间范围、机构范围、所选素材和“是否只使用已复核内容”。当前结构化草稿主要负责数据质量检查和章节骨架，章节仍会标记为 needs_analysis，并没有假装已经生成一份成熟的长报告。项目级导出支持 Markdown、JSON 和 Excel；早期 DOCX、PPTX 生成路由继续保留，但与新的证据型报告项目分开。

为什么使用 Next.js、Supabase 和 Vercel

前端和服务端放在同一个 Next.js 16 App Router 仓库中。React 页面负责九个工作区的交互，Route Handler 承担机构主数据、素材、审核、分析、导入导出和报告 API。这个拆法没有引入复杂的前端状态框架，页面直接读取各自的 API，规模不大时足够直白；代价是请求状态和错误处理分散在不同页面里。

业务数据使用 Supabase PostgreSQL，附件和导出包放在私有 Storage。页面与 API 一起部署在 Vercel，服务密钥只由服务端模块读取。仓库里仍保留早期 Cloudflare D1、R2、Vinext 和 Drizzle 原型，但它们已经从当前 TypeScript 生产构建中排除，不再是线上数据源。

项目也不是从空白开始手写所有界面，更不是把某个现成的竞品情报产品换了名字。第一版基于 OpenAI Sites 的 Vinext / Next.js 通用全栈脚手架，并借助 AI / Codex 很快搭出了可操作的前端原型，当时还有本地 seed 数据和给 KPI 人为 +20、+15 的演示逻辑。后续工程化改造才把它迁到 Supabase，补上真实聚合、状态拆分、审核箱、证据编号、分析版本、批量导入和外部 AI 交接。AI 缩短了原型阶段，但把原型变成可运行系统，仍然依赖数据模型、失败路径、迁移和验证这些普通工程工作。

当前边界比功能清单更重要

目前版本适合单组织、可信成员使用的内部工作台，还不能当作安全完备的公开 SaaS。虽然 Supabase service role 没有进入浏览器、Storage 使用私有 Bucket，新表也启用了 RLS，但源码层还没有真正接入登录、组织隔离和路由权限校验。仓库里存在一份 ChatGPT 登录辅助代码，但当前页面和 API 并没有使用它。正式开放前，这部分必须先补齐。

另外还有几项明确限制：监测需要手动运行；模型调用没有完整的超时与重试策略；大 ZIP 和批量分析仍是同步任务；查重还没有向量语义相似度；社交平台登录态内容、OCR 和完整 E2E 测试也未完成。现有 5 个测试主要锁定架构约束和文件契约，不等于真实 Supabase API 已被自动化覆盖。

对我来说，竞见最值得保留的思路不是“给竞品研究加一个智能体”的说法，而是把 AI 放在证据、审核、版本和人工确认之间。模型可以失败，也可以更换；原始材料、判断依据和业务流程不能跟着一起消失。
