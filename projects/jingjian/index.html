竞见：把淘宝竞品调研做成一套可恢复、可验收的研究工作台

竞见是我们自研的淘宝竞品研究工作台。这篇文章从最新代码出发，拆解研究任务、淘宝采集、人工接管、质量门禁、PPTX 交付与历史报告知识问答的完整实现。

很多“AI 生成 PPT”产品的演示路径都很短：输入一句话，等模型输出一份文件。真正把它用于竞品研究时，麻烦却往往发生在这条直线之外——品牌是否属于目标品类、价格和商品图从哪里来、淘宝登录失效怎么办、任务跑到一半能否继续，以及最后那份 PPT 到底能不能交付。

竞见要解决的并不是“让模型多写几页”，而是把这些不稳定环节组织成一条能追踪、能暂停、能恢复、也能拒绝半成品的研究流水线。

本文界面截图来自最新编译版本，使用脱敏演示数据；真实淘宝、模型和搜索链路仍需在运行环境中单独验收。

从一句需求，变成一份可执行的研究简报

新建调研时，用户给出的不只是一个主题，还可以补充品类、市场、受众、研究目标、指定品牌、价格带和种子链接。快速、标准、深度三种模式，本质上是不同的品牌数与商品数预算；需要更细时，也可以直接自定义。

新建调研：先把一句需求整理成有范围、有预算的研究简报。

提交之前，前端会先检查内容模型、浏览器、淘宝登录态和采集 worker 是否就绪。请求本身带有幂等键，即使用户重复点击或网络重试，也不会悄悄创建两份相同任务。通过检查后，它才会成为一个持久化任务，而不是浏览器关掉就丢失的一次聊天。

一条完整任务大致会经过：

研究简报 → 品类边界 → 品牌发现与核验 → 单品牌研究 → 跨品牌洞察 → 淘宝商品采集 → 内容与视觉检查 → HTML 预览与 PPTX 交付

这里最关键的设计，是没有让一个大提示词包办全部工作。品类理解、品牌发现、品牌档案和跨品牌洞察分别处理；公开资料先被压缩成结构化证据，再交给模型整理。品牌研究可以小规模并发，而依赖共享淘宝浏览器的采集保持串行，避免多个任务争抢同一个登录态和页面。

让失败成为流程的一部分

长任务最怕“跑了二十分钟，最后只得到一个失败提示”。竞见把任务拆成明确阶段，并在品牌完成、采集完成等节点保存检查点。服务重启后，原本正在执行或等待人工输入的任务会进入“已中断、可继续”状态；用户主动继续时，系统会核对请求指纹，复用已经完成的结果，只补尚未完成的部分。

任务状态也不只分成功和失败。排队、运行、等待人工输入、中断、取消中、已取消、完成和失败都有独立语义。进度里保存真实的 current/total、成功数、复用数和阶段耗时，不用一个不断增长的假百分比制造“马上就好”的错觉。

运行中心：演示数据用于展示容量、依赖状态和阶段统计的实际界面。

运行中心把这些信息集中起来：当前容量、任务成功率、中位与 P95 用时、模型和浏览器依赖、采集 worker 心跳、阶段统计、失败位置与备份状态都能直接看到。它更像一个本地研究工作台的控制面板，而不是生成按钮旁边的一条进度条。

淘宝采集不是“再找一张差不多的网图”

商品图、价格、销量线索和规格必须来自同一个商品证据上下文，才能在报告里互相对应。竞见会根据品牌和产品槽位生成稳定的采集任务，通过共享 Chrome 的 CDP 会话搜索淘宝、筛选候选、滚动页面并截取实际商品卡；每个结果记录来源、槽位、时间和状态，失败项可以单独重试，已经合格的结果会被复用。

淘宝登录或验证码无法被当成普通异常自动重试。遇到这类情况，任务会进入“等待人工输入”，前端展示远端浏览器画面，让用户自己完成登录或验证，再从原阶段继续。这个机制的目标不是绕过平台风控，而是承认真人验证本来就是采集流程的一部分。

如果开启淘宝采集却一张可用图片都没有，流水线会停止，不会换成无关的网络占位图继续生成一份看似完整的报告。

报告能打开，不等于报告能交付

研究数据完成后，系统先用同一份结构化数据生成分页 HTML，再以 1280×720 的固定画布逐页渲染成 PPTX。这样浏览器预览和正式演示稿使用同一套排版来源，不需要维护两套很容易走样的模板。页面中可见的来源链接，会在 PPTX 中按原位置重建为可点击区域。

最终交付是一份 PPTX，同时保留同内容的 HTML 预览。需要说明的是，PPT 页面以高保真图像承载视觉内容，链接可以点击，但正文不是一组组原生 PowerPoint 文本框，因此它更适合直接汇报和分发，而不是逐字拆开重排。

生成之后还有最多三轮有上限的质量闭环：

  1. 检查品牌数量、字段完整度、公开来源、品类污染和品牌间重复文案。
  2. 检查图片能否解码、尺寸是否合理，是否出现二维码、登录页或重复图片。
  3. 用浏览器检查每一页的越界、重叠和商品卡溢出。
  4. 对能够定位到具体槽位的图片问题定点补采，再重新渲染和复核。

如果阻断问题在修复轮次内仍然存在，任务会以 quality_gate_failed 结束，而不是把半成品标成“已完成”。这套失败关闭的策略，比“无论如何先给用户一个文件”更接近真实交付。

研究完成后，结果还能继续被问

新版增加了知识问答工作区。已经完成的报告会被拆成报告概况、品牌、商品、市场洞察和建议等小块，写入本地 SQLite。检索时同时使用 FTS5 关键词排名和向量相似度，再通过 RRF 融合两路结果；没有外部 embedding Key 时，仍能使用本地稳定向量，配置 Ark embedding 后再切换到外部语义向量。

研究问答：回答与服务端校验过的来源一起呈现。

可选的模型精排只作用在生成式问答的候选证据上，而且默认关闭。候选内容会被当成不可信数据，模型只能返回服务端发放的候选 ID；超时、格式错误、ID 缺失或重复时，系统直接退回原来的融合排序，不让一次精排失败拖垮问答。

回答中的 [S1]、[S2] 不是模型随手写的装饰。服务端会校验引用是否确实来自本次返回的证据，并把来源快照与会话一起持久化。流式回答中断后，已经生成的部分也会保存；同一个 request id 重试时可以恢复，而不是重复创建一轮回答。

像“目前有多少份报告”“列出全部调研”这类全库问题，则直接查询 SQLite 的完整目录，不把 Top-K 检索结果误当成全量数据，也不必为了一个计数调用模型。

技术架构：围绕长任务，而不是围绕聊天框

层次主要职责与技术
Web 工作台React 19、TypeScript、Vite、React Router、TanStack Query；负责深链接、任务状态、流式问答、移动端导航和配置界面。
API 与编排FastAPI、Pydantic、asyncio；把报告命令、查询交付、RPA 会话、知识库、设置和运维拆成独立路由与服务。
研究与采集OpenAI-compatible 模型接口、公开搜索链、Playwright、共享 Chrome CDP；品牌研究有限并发，淘宝采集单队列运行。
持久化原子 JSON 任务账本、任务检查点、RPA 文件协议，以及用于知识索引和会话的 SQLite/WAL。
交付与验收HTML 分页渲染、PPTX OOXML 打包、布局检查、视觉检查、定点补采和结构化失败码。

后端入口现在主要负责依赖组装，业务分别放在 router、service、pipeline 和知识/RPA 子域里。项目还用架构测试限制组合根和核心 facade 重新膨胀，并检查模块依赖方向。换句话说，这次拆分不是一次性的“整理代码”，而是把不允许退回的大文件和反向依赖写进测试。

前端生产构建由 FastAPI 统一托管，浏览器工作流覆盖深链接、对话框焦点、报告入口、设置保存、带来源的流式回答、幂等新建任务，以及 390px 移动端没有横向溢出。后端测试则覆盖状态恢复、检查点、单队列、定点补采、报告打包、知识检索、会话与精排降级。真实淘宝账号、外部模型和搜索服务仍然需要单独做小任务验收，自动化测试不会假装替代这些外部环境。

目前的边界

竞见当前定位仍是本地工作站工具，不是一个已经做完多租户和分布式队列的 SaaS。任务账本面向单节点、单进程；ShadowBot 兼容模式下，淘宝采集容量固定为一个任务。完整采集需要 Windows 可交互桌面、Chrome 或 Edge、有效淘宝登录态和人工处理验证，网页结构或平台风控变化也可能影响成功率。

正式报告必须有可用的内容模型；专业搜索 API、外部 embedding、可选精排和模型视觉审查可以按需要配置。知识库在没有 embedding Key 时仍可本地检索，但生成自然语言答案依然需要内容模型。

这些限制并不漂亮，却决定了系统是否可信。竞见这次迭代真正完成的，不是把“生成 PPT”包装得更神奇，而是把研究、采集、人工接管、质量门禁、恢复和知识复用连成一条可以观察、可以解释、也允许失败的工程流程。
